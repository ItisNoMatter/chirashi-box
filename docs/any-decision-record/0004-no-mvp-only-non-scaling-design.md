# 0004: MVPの規模でしか成り立たない設計は採らない

- Date: 2026-10-10
- Status: Accepted
- Category: process
- Deciders: the user

## Context
会場の扱いを検討する中で、「既存の会場一覧を丸ごとLLMのプロンプトに入れる」「新しく作られた会場は開発者が手で確認する」という案が出た。どちらも、利用者が招待制の数人に限られるMVPの規模を前提にしており、会場数や利用者が増えると破綻する。

## Decision
MVPの規模（数人・数十館）だから成り立つ、という理由だけで設計を選ばない。データ量や利用者が増えたときに、開発者の手作業やプロンプトのサイズが比例して増えていく設計は避ける。人の確認が必要な場合は、開発者に集中させず、その操作をするユーザー本人に分散させる。

## Alternatives
- MVPの規模を前提に、手作業での確認やプロンプトへの全件投入を許容する: 規模が大きくなったときに作り直しが必要になり、作り直すまでの間はデータの誤りに気づけない。

## Consequences
- 0003の「すり抜けた重複はSupabaseのダッシュボードで手でマージする」は、この方針に反するため見直す。
- 機能をMVPから外すこと（スコープを絞ること）は引き続き許容する。この方針が対象にしているのは、MVPに入れた機能の作り方。
