# 0009: 巡回対象はDBで管理し、自動での追加は後から足せる形にする

- Date: 2026-10-11
- Status: Accepted
- Category: architecture
- Deciders: the user, Claude Code

## Context
前の会話と0005では、館ごとの展覧会一覧ページのURL（とplace_id）を、リポジトリ内の設定ファイルで管理する想定だった。巡回対象を増やす作業は、利用者の数ではなく会場の数（地域の広がり）に比例して増える。将来は、URL登録が多い会場（＝ユーザーが実際に行く会場）を自動で巡回対象にしたい。

## Decision
巡回対象（会場ごとの展覧会一覧ページのURLなど）はDBで管理する。MVPでは、最初の数十館を開発者が投入する。自動での発見・追加は今は作らないが、後から機能を足すだけで導入できる形にしておく。0005の「巡回の対象館は設定ファイルにplace_idを書いておく」は、「巡回設定が会場（place_id）に紐づく」と読み替える。

## Alternatives
- リポジトリ内の設定ファイルで管理し、開発者が追加する: 巡回対象を増やすたびにコミットとデプロイが必要になる。巡回対象がコードに埋め込まれるため、自動化しようとしたときにデータへの移行（作り直し）が必要になる（0004）。
- 最初から自動で発見する仕組みを入れる（URL登録が一定数を超えた会場について、LLMがWebサイトから一覧ページを探し、試しに抽出できれば追加）: 方向としては正しいが、MVPの規模ではURL登録が少なすぎてほとんど発動せず、検証できない。自動で加えた対象が無意味なページを巡回し続けないよう、監視の仕組みも要る。

## Consequences
- 設定ファイルと違って、変更履歴がgitに残らない。必要なら更新日時と更新者の列で補う。
- 自動発見は、URL登録の量が十分に溜まった段階で追加を検討する。
