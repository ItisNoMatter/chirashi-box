# 0005: 会場の同一性をGoogle Places APIのplace_idで決め、見つからない場合は登録者本人に選ばせる

- Date: 2026-10-10
- Status: Accepted
- Category: architecture
- Deciders: the user, Claude Code

## Context
展示の重複判定（0003）は「同じ会場」を前提にしているため、すべての展示が1つの会場に紐づいている必要がある。巡回では会場が設定ファイルから分かるが、URL登録ではLLMが本文から抜き出した会場名の文字列しかない。また、URL登録で拾いたいギャラリーの小さな展示は、既存の会場データにないことが多い。最初は「抜き出した名前で照合し、なければ未確認の印付きで自動作成、確認は人が行う／LLMに既存の会場一覧を丸ごと渡して判定させる」案を検討したが、規模が大きくなると成り立たない（0004）。

## Decision
- LLMは会場名と住所を抜き出すだけにする。
- それをGoogle Places APIで検索し、返ってきた `place_id` を会場の同一性のキーとしてupsertする。
- 巡回の対象館は、設定ファイルに `place_id` を書いておく。
- URL登録では、照合した会場を登録者に表示し（例：「会場：森美術館（港区六本木）で合っていますか？」）、検索で見つからない場合や違っていた場合は、登録者本人が場所を検索して選び直す。

## Alternatives
- 会場は管理者が登録したものだけにする: 知らないギャラリーの展示を登録できず、URL登録の目的と矛盾する。登録のたびに開発者の作業待ちになる。
- 名前で照合し、なければ自動作成する: 「森美術館」と「森美術館（六本木ヒルズ森タワー53階）」のような揺れで会場が二重になり、0003の照合が静かに壊れる。
- 未確認の印付きで自動作成し、人かLLMが確認する: 人が確認する案は、利用者に比例して作業が増える。LLMの判定（既存の会場一覧を渡す、または `pg_trgm` で候補を絞って渡す）は確率的なままで、誤って統合されても検知できない。誤った統合は、展示を無関係な会場や展示に紐づけてしまう。
- OpenStreetMap（Nominatim）のIDを使う: 無料で保存の条件も緩いが、日本の小さなギャラリーの登録はGoogleよりかなり薄い。公開サーバーには利用制限があり、規模が大きくなると自前でホストすることになる。

## Consequences
- 表記の揺れに関係なく、同一性が決定的に決まる。開発者による確認作業は不要。
- 座標と住所が手に入るので、「近くで」やエリアでの絞り込みに使える。
- 外部APIに依存し、使った分だけ課金される。料金と無料枠は実装前に確認する。
- Googleの規約上、`place_id` 以外のデータ（座標など）を保存できる期間には制限があるはず。何をどれだけ保存してよいかは、実装前に確認する。
- URL登録の画面に、会場の確認と選び直しのUIが必要になる。
