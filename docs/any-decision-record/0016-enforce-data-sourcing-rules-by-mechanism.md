# 0016: データ取得のルールを、人の注意ではなく仕組みで守る

- Date: 2026-10-11
- Status: Accepted
- Category: architecture
- Deciders: the user, Claude Code

## Context
前の会話で、取得のルールとして次の点が決まっていた（弁護士の判断ではない）。
- 保存するのは事実の項目（展示名・会場・会期・URL）だけ。美術館が書いた解説文は著作物なので保存しない。
- まとめサイト（TABなど）からは取らない。事実の集まりでも、丸ごと複製して競合サービスに使うと不法行為にあたるとした判例があり、利用規約違反にもなりやすい。
- 各館の利用規約とrobots.txtを確認し、取得は1日1回程度にする。

これを人の注意だけで守ろうとすると、URL登録でまとめサイトのURLが貼られた場合や、館が後からrobots.txtで巡回を禁止した場合に抜けてしまい、0004にも反する。

## Decision
- 抽出のスキーマに、解説文を入れる項目を作らない。
- robots.txtは、巡回でもURL登録でも、取得するたびに機械的にチェックし、禁止されていれば取得しない。User-Agentには、アプリ名と連絡先を名乗る。
- 利用規約は、巡回対象に会場を加えるとき（0009）に人が1回だけ確認する。
- URL登録では、ページを出したのが誰かを次の順で判定し、第三者のページなら登録を断る。
  1. 会場の公式サイト（Placesから得たもの）と同じドメインなら、公式として扱う。
  2. 拒否リスト（DBで管理し、最初に主要なまとめサイトを数件入れる）にあるドメインなら、即座に断る。
  3. それ以外は、抽出と同じLLMの呼び出しで `publisher: "venue" | "organizer" | "third_party"` を判定させる。
- 断るときは「公式ページのはずなら、会場のページのURLを貼ってください」と案内する。

## Alternatives
- まとめサイトの拒否リストを手動で登録するだけ: 決定的で単純だが、知らないまとめサイト（個人のブログやイベント情報サイトなど）は素通りする。
- LLMの判定だけにする: 知らないまとめサイトも弾けて追加費用もほぼないが、会場の公式サイトのような明らかなケースまで確率的な判定に任せ、正しい登録を誤って断ることがある。

## Consequences
- 判定の経路が3つになる。考え方は0006と揃えている（決定的に判定できるところは決定的に、残りだけLLMに）。
- 利用規約の確認は、会場の数に比例する作業で、利用者の数には比例しない。
- LLMが公式の特設サイトを誤って断る場合があるが、会場のページのURLを貼るという別の経路で登録できる。
