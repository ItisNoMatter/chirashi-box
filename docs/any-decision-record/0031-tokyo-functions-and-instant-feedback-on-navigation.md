# 0031: サーバー処理を東京で動かし、画面の切り替えは押した瞬間に反応させる

- Date: 2026-10-13
- Status: Accepted
- Category: architecture
- Deciders: the user, Claude Code

## Context
友人から「動作が重く感じる」と言われた。本番を測ると、ページの枠が届いてからデータの部分が届くまで、毎回約0.85秒かかっていた（全体で1〜4秒）。データベースへの問い合わせは並べて1往復で済ませていたので、遅さは往復の距離にあると見た。Supabase は東京にあるが、Vercel の Function Region は既定のアメリカ東部（iad1）だった。
もう一つの原因は画面の側にあった。眺めるページのタブやエリアのチップは同じページの中の切り替えなので、次のデータが届くまで前の画面が残り、押せたのかがわからなかった。待つあいだの表示も「読み込み中…」の1行だけで、データが届くと画面が大きく動いた。

## Decision
- Vercel の Function Region を東京（hnd1）にする（ユーザーがダッシュボードで変更）。
- タブとエリアのチップは、押した瞬間に選択の表示を切り替え（useOptimistic）、次のデータが届くまでチラシのグリッドを仮のカードにする（useTransition と router.push）。リンクの先読みとアクセシビリティのため、要素は Link のままにする。
- Suspense の fallback を「読み込み中…」から、読み込み後と同じ形の仮の表示（チラシのグリッド、詳細、マイページ）に置き換える。

## Alternatives
- 画面の側の改善だけにする：待ち時間そのものは縮まらない。region を変えるだけで、1秒前後が0.3秒前後になった。
- region の変更だけにする：しばらくアクセスがなかったあとの最初の1回（約1秒）や、モバイル回線の遅さは残る。待つあいだの見え方は変わらない。
- タブを押したら Suspense に key を付けて fallback を出し直す：searchParams を Suspense の外で読むことになり、Partial Prefetching で共有する枠（App Shell）が URL ごとに分かれてしまう。
- `useLinkStatus` で押したリンクに小さな印を出す：押せたことはわかるが、前の画面が残ったままなので、グリッドの中身が切り替わったように見えない。

## Consequences
- 計測（自宅の光回線から）：region を変える前は、ページ全体の受け取りに1.0〜3.9秒かかっていた。変えた後は0.24〜0.42秒。手元の確認では、タブを押してから選択の表示が変わるまで約9ミリ秒、チラシを押してから詳細の仮の表示が出るまで約5ミリ秒。
- 速い切り替えでは、仮のカードが一瞬だけ出て消える。気になるようなら、出すまでに100ミリ秒ほどの遅れを入れる。
- Vercel の region はコードではなくダッシュボードの設定にある。プロジェクトを作り直すときは、設定し直す必要がある。
