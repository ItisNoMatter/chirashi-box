# 0006: 名前で一致しない重複候補は、URL登録では登録者が、巡回ではLLMが判定する

- Date: 2026-10-11
- Status: Accepted
- Category: architecture
- Deciders: the user, Claude Code

## Context
0003の照合では、同じ会場で会期が重なる候補があっても、展示名が一致しない（例：「ルーヴル美術館展」と「ルーヴル美術館展 愛を描く」）と、別の展示として登録されてしまう。0003では、すり抜けた重複をSupabaseのダッシュボードで手でマージするとしていたが、これは0004の方針（MVPの規模でしか成り立たない設計は採らない）に反する。なお、候補は「同じ会場 × 会期が重なる」に絞られるため、データ全体の量に関係なく数件にとどまる。

## Decision
0003の手順2で、候補はあるのに展示名が一致しない場合の判定方法を、経路ごとに分ける。
- URL登録：登録者に候補を表示し、「すでにある『〇〇展』と同じ展示ですか？」と確かめる。
- 巡回：候補の展示名・会期・URLと、新しく取得したページの抽出結果をLLMに渡して判定させる。統合した場合は、その根拠を `exhibition_sources` に残す。

ダッシュボードで手でマージする運用はやめる。

## Alternatives
- どちらの経路でも人に判定させ、巡回では候補があれば新しい展示として登録する: 巡回には聞く相手がいないため、館がページ上で展示名を少し変えた場合などに、巡回同士の二重登録を防げない。
- どちらの経路でもLLMに判定させる: 人に聞ける場面でも、わざわざ確率的な判定に頼ることになる。誤って統合すると、無関係な展示に「気になる」が混ざる。

## Consequences
- 判定の経路が2つになり、テストすべきケースが増える。
- 0005でLLMによる会場の判定を却下した理由（候補の母数が大きい、誤りを検知できない）は、ここでは当てはまりにくい。候補は数件で、会場と会期という強い手がかりがあり、根拠も残る。
- URL登録の画面に、重複候補を確かめるUIが必要になる（0005の会場の確認と同じ流れに並べる）。
