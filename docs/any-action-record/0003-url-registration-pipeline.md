# 0003: URL登録の抽出パイプラインを実装した

- Date: 2026-10-11
- Related AnyDR: 0005, 0008, 0016, 0020, 0021

## Objective
巡回で拾えない展示を、利用者が公式ページのURLを貼るだけで登録できるようにする。「URLを貼る → 取得 → 抽出 → 会場の確認 → 重複の確認 → 登録」の流れを、0005・0006・0008・0016の決定どおりに作る。

## Action
- 実装の前に、Google Places APIの規約と料金を調べた。保存してよいのが `place_id` だけだと分かったため、会場の名前と住所は館のページから取る形に見直した（AnyDR 0020）。確認を待つ間の抽出結果の持ち方もgrillで決めた（AnyDR 0021）。
- ページの読み取り（本文・ハッシュ・og:image）、URL登録の開始・確定、住所からのエリアの導出を、合意した境界からテストファーストで書いた。外部（HTTP・Claude・Places・DB）はポートの向こうに置き、テストでは偽物に差し替えた。
- アダプターを書いた：robots.txtを守りSSRFを防ぐHTTP取得（Shift_JIS対応）、構造化出力によるClaudeの抽出、Google Places、Supabaseのストア。
- 登録待ちと試行の記録（レート制限）のテーブルとRLS、メールの確認コードで匿名ユーザーにメールを紐づける画面、確認コード入りのメールテンプレートを追加した。
- メールの紐づけは、ローカルのSupabaseとMailpitに対するスクリプトで確かめた。

## Result
- 単体テスト47件、RLSのテスト12件、型チェック、lint、本番ビルドがすべて通った（コミット `281443d`）。
- 匿名ユーザーにメールを紐づけても同じアカウントのままで、「気になる」が引き継がれることを確かめた。新規のコードによるログインも通った。
- 本物のClaudeとPlacesはAPIキーがないため、まだ呼んでいない。

## Reflections
- 「規約は実装前に確認する」と0005に書いておいたことが効いた。調べると、Placesから保存してよいのは `place_id` だけで、会場の名前・住所・Webサイトを保存する初期スキーマの前提は規約に反していた。確認を後回しにしていたら、データを作り直すことになっていた。事実の確認は、その事実に依存する実装の直前に置くのがよい。
- ローカルのSupabaseの既定（`enable_confirmations = false`）では、匿名ユーザーの `updateUser({ email })` が確認コードなしにそのまま通り、他人のメールアドレスを名乗れる状態だった。「成功した」だけで止めず、DBの中身（`email_change_sent_at` が null）まで見たことで気づけた。ローカルの認証設定は本番に合わせておくべき。
- Supabaseの既定のメールテンプレートにはリンクしかなく、6桁のコードが入っていなかった。PWAではコードが必須（0008）なので、テンプレートも設計の一部として扱う必要がある。本番のSupabaseにも同じ設定が要る。
- レート制限を「登録待ちと登録済みの数」で数えると、断られた試行（展示ページではない等）が数に入らないのに、LLMの費用はかかる。費用が発生する単位（試行）で数えるべきだと、実装の途中で気づいた。
