# 0001: 設計を詰めて記録し、ひな形・スキーマ・判定ロジックをテスト付きで立ち上げた

- Date: 2026-10-11
- Related AnyDR: 0002, 0018

## Objective
チラシミュージアムの代わりとして、友人のういぴさん向けに作るchirashi-boxの実装を始める。claude.aiでの事前の会話で出ていた要件と構成案を、実装できる粒度の決定に落とし込み、最初に動くひな形を作る。

## Action
- grill-with-docsで、1問ずつ設計を詰めた（19問）。決定はAnyDR 0001〜0018に、用語（展示・チラシ・会場・エリア・会期・気になる・マイページ）は `CONTEXT.md` に、その都度書き出した。途中でユーザーから「MVPの規模でしか成り立たない設計にはしたくない」という方針が出たため、0004として記録し、会場の同一性・重複の解消・巡回のコストの決定をこの方針で見直した。
- 親リポジトリから独立させて `git init` し、GitHubにprivateリポジトリを作ってpushした（コミット `b66cc00`）。
- Next.js 16.4（App Router）のひな形を、既存ファイルとの衝突を避けるため一時ディレクトリで生成してから移した。
- Supabaseの初期スキーマとRLSを書き、pgTAPでRLSのテストを書いた。
- 会期の状態・マイページの並び・展示の照合・出どころの判定を、合意した3つの境界からテストファーストで実装した。

## Result
- RLSのテスト（pgTAP）：9件すべて成功。
- 判定ロジックのテスト（Vitest）：16件すべて成功。`tsc` と `eslint` もエラーなし。
- 照合で「展示名を含む候補が複数ある」ケースはQ&Aでは決めていなかったため、誤って統合しないよう `ambiguous` に倒した。

## Reflections
- 「MVPだから手作業でいい」をやめると決めたことで、設計の質問の多くが「人の確認を誰に分散させるか」「決定的に判定できるところと確率的な判定の境目はどこか」という同じ形に収束した。会場の同一性は外部ID（place_id）で決定的に、重複は候補を絞ってから人かLLMに、出どころは「ドメイン一致 → 拒否リスト → LLM」の順に、と、どれも同じパターンで設計できた。
- Supabaseのローカル環境が起動しなかった原因は、既定のポート（54320〜54329）がすべて、Windows（Hyper-V）が予約しているポート範囲（54262〜54361）に入っていたことだった。`netsh interface ipv4 show excludedportrange protocol=tcp` で予約範囲を確かめ、5532x番台に移して解決した。Windowsで開発するなら、最初に確認しておくべき点。
- create-next-appの既定の `@types/node@^20` は、Vitest 5のpeer dependencyと衝突した。実行環境（Node v24）に型を合わせるのが正しい直し方だった。
- Next.js 16が同梱する `AGENTS.md` には「学習データのNext.jsとは違うので、`node_modules/next/dist/docs/` を読め」とある。画面の実装では、記憶ではなく同梱のドキュメントを先に読む必要がある。
